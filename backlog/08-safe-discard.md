# 08. Восстанавливаемый и атомарный discard

## Цель

Вернуть удаление изменений как recoverable-операцию без частичного успеха и без безвозвратного удаления untracked-файлов.

## Анализ

Сейчас discard обрабатывает файлы последовательно и применяет reverse patch непосредственно к worktree. Ошибка на позднем файле оставляет ранние уже изменёнными. Untracked-файл удаляется через `rmSync`, минуя корзину и backup. Это неприемлемо для функции, работающей с единственной копией незакоммиченного кода.

## Зависимости

- Эпики 01, 02, 05 и 06.
- Использует coordinator эпика 05 и не должен выпускаться раньше safe commit только из соображений порядка релиза; технически независим от эпика 07.

## План реализации

1. Сформировать полный план discard по всем файлам без мутаций.
2. Проверить применимость всех reverse patches (`git apply --check`) к snapshot состояния.
3. Создать durable backup/journal, включая байты untracked-файлов, permissions и symlink metadata.
4. Построить результат в staging-каталоге либо применить единый проверенный patch с rollback protocol.
5. Заменять/удалять файлы только после повторной проверки snapshots; не следовать symlink за границы repo.
6. При любой ошибке откатывать весь набор, а не оставлять частичный результат.
7. Предоставить Undo последнего discard и просмотр backup diff.
8. Удалять metadata changelist только после подтверждённого завершения операции.
9. Добавить тесты partial failure, disk error, symlink swap, untracked content, staged sync и crash recovery.

## Критерии качества и приёмки

- Результат многофайлового discard атомарен с точки зрения пользователя: удалены все выбранные изменения либо ни одного.
- До операции существует recoverable backup; Undo восстанавливает точные байты и staged-состояние.
- Untracked-файлы не удаляются без сохранённой копии и не перемещаются за пределы разрешённого storage.
- Symlink не позволяет читать, перезаписывать или удалять цель вне repository root.
- Ошибка на любом файле оставляет весь worktree/index в исходном состоянии.
- После crash recovery состояние соответствует либо полностью `before`, либо полностью `after`, но не смеси.
- Modal confirmation показывает количество файлов/hunks и срок хранения backup.
