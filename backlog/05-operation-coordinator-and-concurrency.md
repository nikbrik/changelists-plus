# 05. Координатор операций и защита от конкурентного Git

## Цель

Предотвратить потерю staged-состояния или работу с устаревшей базой при параллельных Git-операциях пользователя, VS Code или другого инструмента.

## Анализ

Отдельные Git-команды используют штатные lock-файлы, но последовательность из нескольких команд не атомарна. Между снимком diff/index, применением patch и восстановлением другой процесс может изменить `HEAD` или index. Текущий алгоритм способен восстановить устаревший staged patch поверх нового состояния. Нужен координатор внутри расширения плюс optimistic concurrency guard относительно внешних процессов.

## Зависимости

- Эпики 01–03.

## План реализации

1. Ввести per-repository mutex/queue для всех изменяющих операций расширения.
2. Перед операцией фиксировать `HEAD` OID и fingerprint index (stat + tree/write-tree hash там, где применимо).
3. Повторно проверять snapshot перед каждым необратимым шагом и перед публикацией результата.
4. При внешнем изменении немедленно останавливаться, не пытаясь автоматически перетереть новое состояние.
5. Обеспечить idempotent cleanup временных index/patch файлов во всех ветках.
6. Блокировать UI-команды на время операции и показывать текущий этап без параллельного повторного запуска.
7. Добавить детерминированные тесты с барьерами, где второй Git-процесс меняет index или HEAD в каждой межшаговой точке.

## Критерии качества и приёмки

- Две изменяющие команды расширения для одного repo никогда не выполняются параллельно.
- Независимые репозитории могут обрабатываться параллельно.
- Любое внешнее изменение `HEAD`/index обнаруживается до перезаписи пользовательского состояния.
- При conflict/concurrent-change worktree и новый внешний index остаются побайтово неизменными.
- После ошибки не остаются lock-файлы или временные index-файлы.
- Тесты покрывают внешнее изменение в каждой точке между командами многошаговой операции.
